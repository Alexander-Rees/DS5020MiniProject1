# DS5020 Mini-Project 1: Customers Like You

A recommender ("customers who bought this also bought...") and a customer map for the fictional retailer
GiftLane, built from the real UCI Online Retail II transactions with Truncated SVD (PCA as the comparison).

## Success targets (J1)

> These targets were written down at the **completion stage**, translating Section 1.4 of the brief into numbers.
> They were not recorded on Day 1. All four are checked against measured values below and at the end of
> `notebooks/model_analysis.ipynb`.

| # | Target (Sarah's request) | Threshold |
| --- | --- | --- |
| 1 | Compressed data much smaller than the full matrix | stored factors (customers + products) <= 10 MB, compared with the full dense matrix |
| 2 | The nightly job is fast | fit + top-10 similar products for every product <= 60 s on our laptop (machine-specific) |
| 3 | Suggestions beat best sellers on purchases the model never saw | model hit rate at 10 > best-seller baseline hit rate at 10, same customers |
| 4 | A customer map marketing can use | 4 customer groups, named from their products and countries |

## Results against the targets

From `reports/results.json` (regenerated by `python model_analysis.py`):

| # | Measured | Met? |
| --- | --- | --- |
| 1 | SVD factors at k = 100: **7.328 MB** (5,473 x 100 customer + 3,687 x 100 product, float64 arrays in memory). The dense matrix would be 161.4 MB (22x larger). The sparse matrix's CSR arrays (values + column indices + row pointers) take 5.0 MB in memory; the compressed `.npz` files on disk are about 1.0 MB each. The factors are *larger* than the CSR arrays but give every product a vector for fast similarity search. | yes |
| 2 | Nightly computation stage **0.71 s** (fit 0.19 s + normalise 0.0003 s + top-10 for all 3,687 products 0.52 s). Kernel benchmark: median of 5 runs on the prepared in-memory matrix, Apple M4, one BLAS thread; times vary by a few hundredths of a second between runs. It excludes raw Excel reading and cleaning, Python imports, loading and saving files, and any deployment or network step, so it is not an end-to-end production runtime. Personalised top-10 for all customers adds 0.79 s. (The whole `model_analysis.py` run takes about 90 s because it does many fits, repeated timings and the evaluation.) | yes |
| 3 | Hit rate at 10: **SVD 23.2%** (444 / 1,913) vs **best sellers 17.4%** (333 / 1,913). Gain of 5.8 points, 95% paired-bootstrap interval for the difference 3.4 to 8.3 points. PCA 22.9% (438 / 1,913): 0.3 points below SVD, a difference this sample does not show to be real (McNemar p = 0.21), which is not the same as proving the two are equivalent. | yes |
| 4 | 4 segments (1,365 / 1,910 / 1,387 / 811 customers = 5,473): high-volume wholesalers (children's ranges), mid-size regular buyers (home decor), smaller regular buyers (children's ranges, party & paper goods), occasional small buyers (mixed gifts). | yes |

Honest caveats: coverage is reported three ways. The cohort is 82.9% of test customers (1,913 / 2,308; 378 have
no training history). It holds 70.7% of held-out (customer, product) pairs (44,727 / 63,252). 89.7% of distinct
test products are in the training catalogue (2,555 / 2,849). Recall at 10 is low for every method (SVD 2.8%,
best sellers 1.2%; the per-customer denominator is all of that customer's held-out catalogue products, not capped
at 10). The evaluation uses one pre-Christmas test window, so the gap could differ in other months. The 1/0
purchase value scored slightly higher than log on hit rate (24.9% vs 23.2%, interval includes 0), but log stays the
main model because it was fixed before testing (R2). See `docs/decision_log.md`.

## Data

UCI Online Retail II, `data/raw/online_retail_II.xlsx` (Chen, 2012, https://doi.org/10.24432/C5CG6D, CC BY 4.0).
`build_matrix.py` reads `data/raw/online_retail_II.xlsx`. If that file is missing it extracts the workbook from a
local `online+retail+ii.zip` in the repository root, and if the archive is absent too it stops and asks you to
download it from https://archive.ics.uci.edu/dataset/502/online+retail+ii. `data/` and the archive are git-ignored:
raw and processed data, and anything containing customer IDs, are kept out of new commits. (The archive was
already committed in `d2ba10f`; it has been removed from the index and is now untracked and ignored, with the local
copy retained. Git history was not rewritten.)

Both sheets together have **1,067,371** invoice lines.

| Sheet | Rows |
| --- | ---: |
| Year 2009-2010 | 525,461 |
| Year 2010-2011 | 541,910 |
| Total | 1,067,371 |

Pipeline counts: 802,634 clean rows; cutoff 2011-10-09 12:50:00; 684,071 training rows; 72,919 held-out rows
(new customer-product pairs only); 45,644 repeat purchases excluded from the test set. The training matrix is
5,473 customers x 3,687 products, with 413,927 non-zeros (97.95% sparse).

## How to run

```bash
python3.12 -m venv .venv               # or: uv venv --python 3.12 .venv
source .venv/bin/activate
pip install -r requirements.txt

python build_matrix.py                  # DE1-DE6: rebuilds the matrix from the raw file (about 30 s)
python model_analysis.py                # ML2-ML7: fits, evaluation, comparison, segments, reports (about 90 s with fresh fits)
python -m pytest                        # 30 tests on small synthetic fixtures
```

Then open `notebooks/model_analysis.ipynb` (kernel: the project `.venv`) and run all cells. Or rebuild the
matrix, models, reports, figures, tests and executed notebook with one command:

```bash
python run_project.py                   # build_matrix -> model_analysis -> pytest -> execute notebook
python run_project.py --skip-matrix     # same, reusing data/processed (no Excel re-read)
python run_project.py --force           # same, but refit every model
```

`run_project.py` does **not** build the memo or slides; see "Memo and slides" below. It runs every step, including
the notebook kernel, with the interpreter that started it, so run it from the activated `.venv`.

**The one command that rebuilds the matrix from the raw file (R6) is `python build_matrix.py`.**

Caching: `model_analysis.py` runs every fit (SVD at k = 10, 20, 50, 100, 200; PCA at 100 and 200; SVD with count
and 1/0 values) in its own fresh Python process, so fit time and peak memory are measured fairly. Results are saved
under `data/processed/models/` and reused on the next run only if the matrix contents, the fitting, scoring,
top-10 padding and measurement code, the settings and the library versions are unchanged (editing only reports or
figures reuses them). `--force` refits everything. Thread counts for numpy/scipy/OpenMP
are pinned to 1, and `MPLCONFIGDIR` defaults to `/private/tmp/ds5020-mpl`. Seeds are fixed (`random_state=42`
everywhere).

## Memo and slides

Built separately by the artifact scripts from the reports, after `model_analysis.py`. They are not portable to an
ordinary system Node or Python on their own: the slides need `@oai/artifact-tool` and the presentation skill's
finalizer, and the memo needs `reportlab`, `pypdf` and `pdftoppm`. All of these come from the Codex runtime and
skill installed on this machine:

```bash
RUNTIME_NODE=/Users/samopk/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node
RUNTIME_PYTHON=/Users/samopk/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3
# Defaults used by the scripts (set these variables only to override):
#   RUNTIME_NODE_MODULES=/Users/samopk/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules
#   PRESENTATIONS_SKILL_DIR=/Users/samopk/.codex/plugins/cache/openai-primary-runtime/presentations/26.1011.11113/skills/presentations
#   PDFTOPPM=/Users/samopk/.cache/codex-runtimes/codex-primary-runtime/dependencies/bin/override/pdftoppm

"$RUNTIME_PYTHON" scripts/create_submission.py memo --replace   # memo (J2) -> output/pdf/memo.pdf
"$RUNTIME_PYTHON" scripts/create_submission.py facts            # shared facts file for the slides
"$RUNTIME_NODE" scripts/create_slides.mjs --replace             # slides (J3) -> output/slides/presentation.pptx
```

Without `--replace`, a new file is written next to an existing one with a time stamp. The generated `memo.pdf` and
`presentation.pptx` are ordinary portable PDF and PowerPoint files; only regenerating them needs the runtime above.
